# 设计取舍说明

产品构想第 8 节建议的技术栈是「Python + pandas + NumPy」。实际实现是 **Python + 纯标准库**。
这里坦白说明为什么这么选，以及代价在哪里。

## 1. 为什么不用 pandas / NumPy

| 维度 | pandas / NumPy | 纯标准库（本实现） |
|---|---|---|
| 安装 | 需要 pip，Python 3.9 上要装 wheel；公司/受限环境常被代理与版本冲突卡住 | 系统自带 Python 直接能跑 |
| 复现 | 不同 pandas 版本的 rolling/ewm 边界行为会有细微差异，回测结论可能因此漂移 | 公式在 `indicators.py` 里显式实现，行为完全确定 |
| 审计 | `ewm(alpha=1/14)` 之类的写法需要读者自己确认是 Wilder 还是 EMA 口径 | 一眼能看懂每行算术，便于核对是否符合经典定义 |
| 性能 | 数万行级别更快 | 160 只 × 420 天的全量扫描 ≈ 0.15 秒；几千只股票 × 数百天的日线在秒级到十秒级 |
| 依赖风险 | 供应链与安全审计面更大 | 无 |

本工具每天只跑一次，处理的是"日线 × 数千只股票"这种规模，纯标准库的速度完全够用；
而"配置门槛 → 复算 → 得到同一份名单"的可复现性对这个项目更重要。所以选择零依赖。

## 2. 代价与应对

* **没有向量化的表达便利**：指标必须自己写。应对方式是全部收敛到 `indicators.py` 一个文件，
  并为每个公式写单元测试（含 Wilder 的经典 RSI 示例、`new_low_streak` 中断条件、成交额变异系数等）。
* **没有现成的技术分析库**：RSI、均线、已实现波动率、低点形态都自己实现，
  好处是口径完全可控（例如 RSI 明确用 Wilder 平滑，而不是某些库默认的 EMA）。
* **内存中保存全部 K 线**：`db.load_bars_map` 一次性读入并按需截断。对全市场（约 6000 只 × 500 天
  ≈ 300 万行）也能承受；如果将来数据量再大一个数量级，可以把特征计算挪到 SQL 里做窗口聚合。

如果确实需要 pandas，`providers/csv_provider.py` 与 `db.py` 的边界很清晰，替换数据层即可，
评分与筛选逻辑不需要改。

## 3. 其他关键取舍

### 3.1 为什么自己实现交易日历

`exchange_calendars` / `pandas_market_calendars` 都很成熟，但它们会引入 pandas 依赖，
而且我们只需要"是不是交易日 / 上一个交易日 / 最近一个已收盘交易日 / 提前收市"这几个能力。
`calendar_us.py` 用 NYSE 的固定与浮动假日规则（含观察日顺延、Juneteenth、耶稣受难日、
感恩节次日等提前收市）实现了这些能力，并为 2021–2028 的关键日期写了测试。
临时休市（国葬、飓风）用 `EXTRA_HOLIDAYS` 显式列出，而不是假装不存在。

### 3.2 为什么"基本面缺失"是 None 而不是 0 或满分

产品构想第 4 节明确要求：没有可靠基本面数据时，不要把 20 分按满分或平均分补齐。
实现上 `score_quality()` 返回 `None`，`ScoreBreakdown.max_available` 相应变成 80，
报告写「XX/80（基本面维度未覆盖）」并降低置信度。这样排名不会被"假数据"扭曲。

### 3.3 为什么风险不用总分抵消

`持续创新低`、`异常波动`、`重大融资稀释`、`退市风险文件` 属于一票降级：
无论总分多高都只能进 B 区观察名单。理由是一个 90 分的"正在自由落体 + 马上要发新股融资"的股票，
不应该因为流动性好、跌得深就排在第一位。

### 3.4 为什么实盘与回测共用同一份 pipeline

很多回测框架的偏差来自"回测用一套简化逻辑，实盘用另一套完整逻辑"。
本项目的做法是 `pipeline.run_scan(settings, session=..., provider=...)` 只有一份实现，
回测只是换了一个"只能看到该日之前数据"的 provider 包装（`HistoricalView`）。
`tests/test_pipeline.py::TestNoLookahead` 会把两种视角下的结果逐一比对，必须完全一致。

### 3.5 为什么输出三种格式

* Markdown：给人读，也是通知脚本的载荷（`reports/latest.md`）；
* CSV：给人做二次筛选（一列一个指标，包含所有分项分数）；
* JSON：给程序读，且可以**不重跑扫描**就重新渲染报告
  （`cli report --session 2026-10-09`，改报告格式时很省时间）。

### 3.6 报告排版：为什么最终用"引用块 + 一行一字段"

中途试过 Markdown 表格，问题有两个：一是表头一多就横向溢出，`vs 50 日线` 这种列在
手机上根本看不到；二是"风险标签""退出观察条件"这类**长短不一的列表**塞进单元格后
只能挤成一行，又变回了大段文字。

最终按产品构想第 6 节的报告示例做：整份报告放在一个引用块里，一行一个字段，
列表类内容用缩进子项展开，每行结尾加两个空格做硬换行。好处是：

* 在终端、手机、GitHub、IM 里都能正常折行，不需要横向滚动；
* 每只股票的字段顺序固定，方便快速扫读和对比；
* 想复制某一段（比如"退出观察条件"）直接选中即可，不会带上表格的管道符。

约束写成了回归测试：最长的行不得超过 200 字符，引用块之外只允许有一行免责声明。
细节（完整风险说明、全部指标）仍然保留在 CSV / JSON / 网页里。

### 3.7 为什么默认主名单是"还在跌"的那一组

产品构想原本建议把**企稳组**当主要候选，理由是胜率更高。这没错，但它和用户
明确表达的偏好（"买跌不买涨"）是**冲突**的：所谓"企稳证据"里的"站上 20/50 日均线"
"RSI 从低位回升"，本身就意味着价格已经在涨了。按企稳组出名单，A 组全是
"回撤很深、但已经转涨"的股票 —— 对买跌的人来说，这就是"涨的股票"。

处理方式不是二选一，而是把选择变成一个显式开关：

* `dip_preference = dip`（默认）：主名单 = 低位且还没涨起来的一组；
* `dip_preference = stabilized`：回到构想原本的策略；
* 无论选哪个，"已经涨起来"（近 1 月 / 近 3 月涨幅超限、RSI 偏高）的股票都**不会进主名单**，
  因为对"低位"这个前提来说，它们已经不成立了。

同时给买跌模式加了护栏：连续创新低、异常波动、退市融资类披露一律一票否决。
否则"买跌"会退化成"专挑自由落体的接刀"。

### 3.8 样本数据的定位

`sample` provider 不是玩具：它按 8 种形态原型合成市场（低位企稳、低位续跌、高位强势、
流动性不足、低价、微市值、中位震荡、异常波动），让**每一条筛选规则都有对应的样本**，
从而可以验证"规则真的在起作用"，而不是只验证"程序没有崩"。
但报告里永远标注数据来源是合成数据，避免被误当成真实结论。

## 3.9 为什么网页仪表板也用标准库

阶段 4 要求「网页仪表板」。常见做法是 Flask/FastAPI + 前端框架，但那会一次性引入几十个依赖，
还要处理构建产物与版本锁定。本工具只需要「读 SQLite → 渲染 HTML」，标准库的
`http.server` 完全够用：没有构建步骤、没有 CDN、没有 node_modules，
断网也能打开，改一行 CSS 刷新即见。

代价是模板得手写字符串，以及没有现成的 ORM/路由。应对方式是：

* 把所有渲染逻辑放进 `webapp.Dashboard` 类，**与 HTTP 层解耦**，可以直接单元测试
  （不需要起服务，沙箱里也能跑）；
* 只有 `/api/*` 需要程序化访问，同样由 `Dashboard.api()` 提供，JSON 与页面共享同一份数据层
  （`history.py`），不会出现「网页上的数字和 CSV 里的对不上」。

## 4. 已知不足（后续可以做的改进）

1. **买卖价差未纳入**：多数免费数据源不提供报价与价差，流动性只用美元成交额近似。
   若接入 SIP 级别的报价数据，可以在流动性维度里加入滚动价差分项。
2. **基本面维度尚未启用**：接口已经留好（`quality_source = csv | sec_edgar`），
   但默认关闭，因为需要用户先准备好可靠的数据源。
3. **行业基准需要自己提供** `sector_map_file`，否则相对强弱只与 SPY 比较。
4. **回测未模拟交易成本**，且股票池存在幸存者偏差 —— 已在报告与 README 中声明。
5. **仪表板没有登录体系**：默认只监听 `127.0.0.1`。要在局域网/公网访问，需要自己加反向代理
   与访问控制，工具不会替你处理鉴权。
6. **通知渠道是「够用」而非「齐全」**：内置邮件、通用 Webhook（Slack/企业微信/钉钉/Telegram）、
   macOS 本地通知；短信、电话告警之类需要自己接。
